つまり「ライフイベント軸の記事 × 計算機」という設計は、**育休・産休の範囲ですでに実装されている。**

## 2. サイトの定義

> **税・教育費・資産形成のお金を、公的機関の原文と自作の計算機で確かめるサイト**

### 扱うものと、扱わないもの

この線引きが、YMYL 領域でこのサイトが成立するかを決める。

| 扱う | 扱わない |
|---|---|
| **規則を適用すれば答えが確定するもの**<br>いくらもらえる／いくら引かれる／条件を満たすか | **意見であり検証できないもの**<br>おすすめ証券口座、銘柄選び、保険の推奨、ランキング |

**扱わない側を明示的に捨てる理由**は2つある。

1. Google の YMYL 評価で、個人サイトが最も勝てない領域である
2. **「公式の原文を引く」という当サイトの売りが一切効かない。**おすすめには原文が存在しない

扱う側は原文が必ず存在し、正しさが検証可能。既存の編集方針（`CLAUDE.md` の「事実の扱い」）がそのまま乗る。

### 一次情報の出典源

国税庁／厚生労働省／日本年金機構／全国健康保険協会（協会けんぽ）／こども家庭庁／文部科学省／
日本学生支援機構（JASSO）／金融庁／e-Gov法令検索／各自治体。

**すべて `CLAUDE.md` が根拠として認めている「公的機関の資料」に収まる。**
他人のブログ・まとめ記事は引き続き根拠にしない。

### 既存サイトとの territory

| 領域 | 担当 |
|---|---|
| 育休・産休・出産手当金・傷病手当金 | **`ikunavi`**（当サイトでは記事を書かない。リンクで送る） |
| 税と社会保険の壁 | **当サイト** |
| 教育費 | **当サイト** |
| 資産形成（NISA・iDeCo・家計） | **当サイト** → `nisa` / `lifeplan` へ送客 |
| 沖縄の上乗せ制度 | **`uchina-money`** へ送る |

## 3. カテゴリ設計

最終形は3つ。ただし `CLAUDE.md` のルール（記事が0本のカテゴリを `site.json` に置かない）に従い、
**`zeikin` の1カテゴリで開始する。**残り2つは1本目が書けた時点で `site.json` に足す。

| slug | 名前 | 中身 |
|---|---|---|
| `zeikin` | 税と社会保険 | 扶養の壁、各種控除、年末調整、ふるさと納税 |
| `kyoikuhi` | 教育費 | 児童手当、高校無償化、奨学金、学資保険 |
| `shisan` | 資産形成 | NISA、iDeCo、家計 |

**`zeikin` から始める理由**: 毎年改定があり、ネットのまとめ記事が古い数字のまま放置されている。
原文を引くことが読者の手取り額を実際に変える領域である。

### 1本目の候補

「扶養の壁」（103万／106万／130万／150万が何の壁で、根拠がどこにあるか）。

⚠️ **`未確認`。**本設計の執筆時点で制度の現在値は記憶からしか参照していない。
記事にする時点で国税庁・厚生労働省のページを実際に取得して確認する（`CLAUDE.md`「記憶から書かない」）。

## 4. 計算機の扱い

**新サイトには計算機を実装しない。**既存の `nisa` / `lifeplan` へリンクで送る。

理由: `harness-core` の「最小から始めて、実測で効果が示されたときだけ足す」。
記事の面が取れるかがまだ検証されていない段階で、計算機5本目の保守を増やす根拠がない。

ただし **「根拠の全開示」は記事側でやる。**
既存の計算機5本はどれも計算根拠を出していないため、**当サイトの記事がその根拠ページになる。**
各記事には「どの条文のどの数字を使ったか／どこを近似したか／当てはまらないケース」を書く。

新サイトへの計算機移植は、記事の流入が実測できてから判断する。

## 5. ビルドガード

制度モノの事故は「**古い数字が記事に残ること**」ただ一つ。
既存の `assertCardNumbers` / `assertNoRawEmphasis` と同じ発想で、機械が検出できる形にする。

| ガード | **実装が実際に検査していること** | 失敗時 |
|---|---|---|
| `sources` / `checkedAt` を front matter で必須化 | 記事に `https://` で始まる出典URLが1本以上あること。`checkedAt` が実在する日付で、ビルド日より未来でないこと | **ビルドを落とす** |
| `checkedAt` の経過日数 | 最終確認日から N 日以上経過している記事を検出 | 警告 |
| **`revisionAt`（次の改定予定日）** | **書かれている記事について**、その日を過ぎていないこと（`revisionAt` は任意項目） | **ビルドを落とす** |
| `assertCardNumbers` | `seido` カードの数値トークンが、同じ記事の表の行にすべて現れること（**記事内の内部整合のみ**） | **ビルドを落とす** |

⚠️ **この表の右列は「実装が検査していること」であり、「事実として正しいこと」ではない。**
機械が見ていないものを、見ているように書かない（`CLAUDE.md`「公式に書かれていないことを、書かれているように書かない」）。とくに:

- **どの数字がどの出典URL由来かは、一切検査していない**（`sources` は記事単位のリストで、名寄せの仕組みが無い）
- **表そのものが事実と合っているかは、誰も見ていない**（`assertCardNumbers` はカードと表の一致だけを見る）
- **`revisionAt` は任意項目。**書かなければこのガードは永久に発火しない
- 残る抜け穴の一覧は `HANDOFF.md`「ガードをすり抜ける経路」に置く

**`revisionAt` が設計の肝である。**
「確認日が古い」は主観だが、「**改定日を過ぎた**」は事実として判定できる。
育休給付金の上限は毎年8月1日、扶養の壁は税制改正、児童手当は改正法の施行日——
改定日が分かっている制度なら、**機械が「この記事はもう嘘かもしれない」と言える。**

これは自己評価ではなく、生成とは独立した検証である（`harness-core`「自己評価を品質の根拠にしない」）。

既存のガード（`assertCardNumbers` / `assertNoRawEmphasis`）は**そのまま移植して残す。**

- `site.json` の `affiliateEnabled` は **`false` のまま開始する。**リンクが0本で開示文言だけ出すのは事実に反する

- `links.json` の台帳方式と `[[AF:キー]]` 記法はそのまま移植する。
  **ASPの管理画面が発行したURL以外を入れない**というルールも変わらない

## 7. 技術構成と移行

| 項目 | 内容 |
|---|---|
| リポジトリ | **新規に切る。**`affi`（`moshimo-affiliate`）は記事3本のまま残す |
| ドメイン | `kakei.nexeed-lab.com` |
| 生成器 | `moshimo-affiliate/site/` の `build.mjs` / `templates/` / `public/styles.css` を移植 |
| デプロイ | Cloudflare Workers Static Assets（既存2サイトと同じ方式） |

### 移植時に差し替えるもの

|---|---|---|

| カテゴリ | `moshimo` / `jissoku` | `zeikin`（開始時は1つ） |
| カードのフェンス | ` ```asp `（service / link / 条件） | ` ```seido `（制度名 / 根拠 / 確認日） |
| タグライン | ASPの条件を、公式の文言で確かめて書く | お金の制度を、公式の原文で確かめて書く |
| front matter | — | `sources` / `checkedAt` / `revisionAt` を追加 |

### 移植しないもの

- 記事3本（`moshimo-*.md` / `jissoku-index-request.md`）— `affi` に残す
- `docs/moshimo-koshiki-kakunin-2026-08-31.md` — `affi` に残す
